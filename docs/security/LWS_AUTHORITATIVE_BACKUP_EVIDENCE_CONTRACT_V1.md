# LWS Authoritative Backup Evidence Contract V1

Status: `DRAFT FOR FUTURE P0-6F - NO IMPLEMENTATION`

Baseline date: `2026-09-05`

This document defines the evidence required before a future server-side verifier could satisfy the P0-3D backup dependency. It creates no table, migration, backup, verifier or purge wiring.

## 1. Purpose And Boundary

The contract proves that one exact purge target, including its required relational records and Storage objects, can be recovered from a retained source. It is not a general backup-health signal and cannot authorize purge by itself. P0-3D retention, trash-first, dual-control, actor, AAL2, velocity and policy checks remain separate mandatory gates.

Current status: `AUTHORITATIVE_OBJECT_BACKUP_EVIDENCE_PRESENT: MISSING`.

## 2. Required Evidence Fields

| Field | Required meaning | Validation requirement |
| --- | --- | --- |
| `evidence_id` | Globally unique immutable evidence identifier | Generated by trusted server authority; never caller-selected for an existing record |
| `action_code` | Exact destructive action the evidence may support | Must match the central policy and purge request |
| `object_type` | Canonical governed object type | Must be allowlisted and coherent with `action_code` |
| `object_id` | Authoritative source object identifier | Must resolve server-side and match the purge target |
| `canonical_object_fingerprint` | SHA-256 of versioned canonical identity and recovery scope | Must be recomputed server-side and match exactly |
| `manifest_version` | Version of canonical manifest schema and serialization | Supported immutable version only |
| `database_records_manifest` | Complete allowlisted database record identities, revisions and checksums | Must cover every required relational dependency and exclude raw secrets |
| `storage_objects_manifest` | Complete bucket/object/version, byte count, MIME and checksum inventory | Required even when empty; actual object existence must be verified |
| `backup_reference` | Immutable provider backup, snapshot or export reference | Must resolve through trusted recovery authority and remain retained |
| `recovery_source` | Provider, account/custody boundary, region and source class | Must identify where recovery bytes and records come from without credentials |
| `provider_account_independence` | Whether recovery survives loss of the primary provider/account | Must be server-verified; same-project-only is false |
| `captured_at` | UTC time at which the recoverable snapshot became complete | Must be authoritative and not future-dated |
| `last_source_mutation_at` | Latest included relevant mutation in UTC | Evidence is invalid when `captured_at` precedes this time |
| `retention_until` | UTC deadline through which recovery source is guaranteed retained | Must exceed verification time and the required purge safety window |
| `object_checksums` | Checksums for required records/artifacts or deterministic groups | Algorithms and canonicalization versions must be explicit; every required item must match |
| `manifest_checksum` | Checksum of the complete canonical manifest | Must be recomputed server-side before acceptance |
| `verified_at` | UTC verification completion time | Must be after capture and within freshness policy |
| `verification_authority` | Immutable identity of approved independent verifier/service | Must not be derived from untrusted caller claims |
| `verification_result` | Exact result such as valid or invalid plus bounded reason code | Only a server-produced valid result can advance evaluation |
| `restore_test_reference` | Immutable reference to the qualifying isolated restore test | Must bind the tested backup, manifest and acceptance evidence |
| `restore_test_at` | UTC completion time of the qualifying restore test | Must satisfy test recency policy and precede verification completion |
| `recovery_status` | Lifecycle state of the evidence | Only current, verified and unexpired evidence is eligible |
| `recovery_expiry` | UTC time after which evidence must fail closed | Must be no later than backup/source retention expiry |

The eventual schema may split these fields across immutable records, but it must preserve one canonical evidence projection with these semantics.

## 3. Canonical Object Fingerprint

The fingerprint input must use a versioned canonical serialization and include at least:

- contract and manifest version;
- action code and object type;
- object ID;
- authoritative lifecycle revision or equivalent concurrency identity;
- sorted database-record identities and revision/checksum values;
- sorted Storage bucket, object path, immutable version/reference, byte count and checksum values;
- last relevant source mutation time.

Ordering, null representation, timestamp format, text encoding and checksum algorithm must be deterministic and documented. A fingerprint generated only from the object UUID is insufficient.

## 4. Manifest Requirements

### Database records manifest

- Include all records that the purge would delete, cascade-delete, anonymize or make unusable.
- Include required parent, child, event, approval, financial, document-metadata and identity-binding references.
- Record stable primary identity, table/schema identity, relevant revision and canonical checksum.
- Exclude passwords, tokens, secret values and unnecessary personal payloads from evidence. Recovery bytes may remain encrypted in the backup source.

### Storage objects manifest

- Include each required bucket and object path, immutable source version/reference, MIME type, byte count and cryptographic checksum.
- Distinguish no required objects from an incomplete inventory.
- Confirm bytes exist in the recovery source; database metadata alone is insufficient.
- Detect missing, unexpected, duplicate and checksum-mismatched objects.

## 5. Verification Authority

1. The caller may request evaluation but cannot submit or override backup-success, independence, capture time, checksums, retention or restore-test results.
2. A trusted server-side verifier resolves backup and object references through bounded adapters.
3. Verification identity and result are append-only and independently auditable.
4. Verification must bind the exact action, object, lifecycle revision, manifest and backup source.
5. Verification must be repeatable without exposing credentials or document contents.
6. Provider telemetry alone is insufficient when it cannot prove object-level inclusion and recoverability.

## 6. Security Invariants

- Evidence is append-only and immutable. Correction creates a superseding evidence record; history remains intact.
- Caller-controlled claims never establish successful backup or restore.
- Evidence must be verified server-side after the last relevant object mutation.
- Every required database record and Storage object must be present in the canonical manifest.
- Any object or manifest checksum mismatch makes the evidence invalid.
- Expired backup retention, evidence freshness or recovery status makes the evidence invalid.
- A missing or stale qualifying restore test makes evidence invalid wherever policy requires that test.
- A same-project-only or same-administrative-account-only copy is insufficient to unblock purge.
- `MISSING`, `UNKNOWN`, timeout, adapter error or ambiguous result fails closed.
- Tombstones, audit metadata, fingerprints and checksums are not restore sources.
- A global statement such as “backup succeeded” without exact object binding is insufficient.
- Database backup evidence cannot satisfy Storage-object coverage.
- Evidence used for purge must survive the purge itself and remain available for its full retention period.
- Restore-test evidence must show integrity and business validation, not merely successful import.

## 7. Eligibility Decision For Future P0-6F

Future evidence is eligible only when all of the following are `PROVEN`:

1. action/object/fingerprint binding;
2. complete database and Storage manifests;
3. capture after the last relevant mutation;
4. valid object and manifest checksums;
5. unexpired retention and evidence status;
6. independent recovery source;
7. qualifying restore test and verification authority;
8. continued satisfaction of every non-backup P0-3D gate.

Any other result is denial. P0-6F must begin in shadow mode and may not change the current P0-3D `BACKUP_EVIDENCE_UNAVAILABLE` outcome. Only P0-6G, after separate OWNER approval, may propose production wiring.

## 8. Explicit Non-Claims

- This contract does not prove that any current backup contains a purge target.
- This contract does not prove that Storage is backed up.
- This contract does not prove that a restore has been tested.
- This contract does not authorize purge, backup, restore, migration, deployment or configuration changes.
