# LWS Local Encrypted Database Backup Foundation V1

Status: `P0-6B LOCAL FOUNDATION - OWNER REVIEW REQUIRED`

Baseline date: `2026-09-05`

## 1. Boundary

This foundation can export and restore only an explicitly identified `LOCAL` or `TEST` PostgreSQL database on `localhost` or `127.0.0.1`. It does not export production data, contact Supabase, upload an artifact, configure an offsite provider, enable PITR, run a migration, deploy code or alter the P0-3D purge gate.

The current operational capability remains:

- production independent/offsite database backup: `MISSING`;
- production Storage backup: `MISSING`;
- production restore evidence: `MISSING`;
- P0-3D authoritative backup evidence: `MISSING`;
- production wiring and purge unblocking: `NO-GO`.

## 2. Package Contract

One package directory contains exactly an encrypted database artifact and its JSON manifest. The machine-readable contract is `scripts/security/backup/backup-package.schema.json`.

The manifest binds:

- `backup_id`, `backup_type`, `captured_at`;
- `source_environment` and a non-secret `source_project_reference`;
- `database_export_filename` and `database_export_sha256`;
- `encrypted_artifact_filename` and `encrypted_artifact_sha256`;
- `manifest_sha256` calculated over canonical manifest content excluding that field itself;
- `encryption_algorithm` and `encryption_key_reference`;
- `retention_until`, `created_by_tool_version` and `schema_migration_reference`;
- `verification_status` and, only after successful cleanup, the local synthetic restore result.

Passwords, JWTs, API keys, service-role keys, signing material and credential-bearing connection strings are forbidden in the manifest. Filenames cannot escape the package directory.

## 3. Encryption And Key Custody

- The plaintext logical dump is encrypted client-side before any future transfer boundary.
- Encryption is authenticated `AES-256-GCM` with a fresh 96-bit nonce per package and a 128-bit authentication tag.
- Each nonce is generated by Node.js `crypto.randomBytes`, backed by the operating system cryptographic random source.
- The artifact contains only a format marker, nonce, ciphertext and authentication tag.
- SHA-256 is calculated separately for plaintext, encrypted artifact and canonical manifest.
- The 256-bit key is accepted only through `LWS_LOCAL_BACKUP_ENCRYPTION_KEY_B64`; it is never generated into or stored in tracked files.
- The key is never stored beside the package. The manifest stores only an operator-provided key reference, allowing rotation and historical lookup through a future approved custody system.
- Plaintext is held only in an isolated temporary directory and removed after encryption or any failure.

Before production approval, key custody must preserve an immutable mapping from every retained key reference to its historical key for at least the corresponding backup retention period. A production-project migration must also add the new project reference to the hard-deny set before any tooling use.

## 4. Hard Local Guard

The tooling fails before command execution unless all conditions hold:

- environment is exactly `LOCAL` or `TEST`; case and whitespace are not normalized;
- host is exactly `localhost` or `127.0.0.1`;
- project reference is a lowercase opaque identifier beginning with `local-` or `test-`, using only ASCII letters, digits and hyphens;
- URLs, hostnames, IP addresses, Supabase domains, credential URIs and any reference embedding production project `xcsptvntvrizwhskaphr` are rejected;
- no URL, DSN or connection-string input is accepted;
- restore environment is exactly `TEST`;
- restore database starts with `lws_restore_test_`.

Database passwords are accepted only through `LWS_LOCAL_BACKUP_DB_PASSWORD` and are passed to local PostgreSQL tools through `PGPASSWORD`. Logs contain fixed event names, backup IDs and reason codes only.

## 5. Local Export

Prerequisites are local PostgreSQL client binaries on `PATH`: `pg_dump`, `pg_restore`, `createdb`, `dropdb` and `psql`.

Example for a local Supabase database only:

```powershell
$env:LWS_LOCAL_BACKUP_ENCRYPTION_KEY_B64 = "<32-byte-key-as-base64-from-approved-local-custody>"
$env:LWS_LOCAL_BACKUP_DB_PASSWORD = "<local-test-password>"
node scripts/security/backup/create-local-backup.mjs `
  --environment TEST `
  --host 127.0.0.1 `
  --port 54322 `
  --database postgres `
  --user postgres `
  --source-project-reference local-supabase-test `
  --output .local-backups `
  --key-reference local-custody-key-v1 `
  --retention-days 30 `
  --schema-migration-reference local-schema-head
```

Do not pass passwords or encryption keys as command-line arguments. `.local-backups/` must remain untracked and must not be synchronized externally without separate approval.

## 6. Local Restore Verification

The verifier checks manifest integrity, encrypted SHA-256, AES-GCM authentication and plaintext SHA-256 before creating a disposable database. It restores with `pg_restore`, counts non-system schemas and tables through `psql`, drops the disposable database, removes temporary plaintext, and only then records `VERIFIED_LOCAL_SYNTHETIC` in the manifest.

```powershell
node scripts/security/backup/verify-local-restore.mjs `
  --package .local-backups `
  --manifest lws-db-example.manifest.json `
  --environment TEST `
  --host 127.0.0.1 `
  --port 54322 `
  --database lws_restore_test_example `
  --user postgres `
  --target-project-reference local-restore-test `
  --key-reference local-custody-key-v1
```

This is not production restore evidence. Only synthetic local data is approved for this phase.

## 7. Offsite Contract

`scripts/security/backup/offsite-provider-contract.mjs` defines future operations for encrypted-artifact upload, manifest upload, remote checksum verification, retention lookup and separately approved deletion after retention. It contains no provider adapter, credentials, endpoint or network call. `OFFSITE_PROVIDER_IMPLEMENTED` remains `nee`.

`retention_until` is metadata only in this local foundation. No deletion implementation exists. Future provider/evidence work must enforce retention and separate OWNER approval before deletion.

## 8. Verification

Run:

```powershell
node --test scripts/security/backup/backup-foundation.test.mjs
```

The suite uses real temporary files and Node cryptography with synthetic dump bytes and an injected local command-runner. It does not require PostgreSQL binaries, open a socket, contact Supabase or retain plaintext.

An opt-in integration test can additionally prove real `pg_dump` and `pg_restore` against two isolated disposable databases inside an already-running local Supabase PostgreSQL container. It creates only synthetic data and never inspects an existing database:

```powershell
$env:LWS_RUN_LOCAL_BACKUP_INTEGRATION = "1"
$env:LWS_LOCAL_POSTGRES_CONTAINER = "<approved-running-local-container>"
node --test scripts/security/backup/backup-foundation.integration.test.mjs
```
